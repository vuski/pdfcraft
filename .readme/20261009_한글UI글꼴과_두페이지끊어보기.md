# 한글 UI 글꼴 수정과 두 페이지 끊어 보기 (2026-10-09)

PdfCraft v0.4.0에서 탭과 북마크의 한글이 □로 깨지는 문제를 고쳤고, 두 쪽씩 끊어서 넘기는 보기 방식을 추가했다. 두 작업은 각각 업스트림 PR로 올렸다. 개인용 빌드에는 PR에 넣지 않은 글꼴 설정까지 모두 적용했다.

| 항목 | 위치 |
|---|---|
| PR 1: 한글 글꼴 | storytold/pdfcraft#507 (`fix/korean-ui-font-fallback`), #407 해결 |
| PR 2: 두 페이지 끊어 보기 | storytold/pdfcraft#508 (`feat/two-page-spread`) |
| 개인용 빌드 소스 | `personal/malgun-first` (이 문서가 있는 브랜치) |
| 개인용 실행 파일 | `C:\program portable\pdfcraft.exe`, 시작 메뉴에 "PdfCraft"로 등록 |

## 1. 한글이 □로 깨지던 원인

- 앱에 내장된 UI 글꼴은 Inter(영문)와 craft-fonts의 일본어 글꼴뿐이다. 릴리스가 고정해 둔 craft-fonts 버전에는 한글 글꼴이 없고, craft-fonts main에도 없다.
- 내장 글꼴에 없는 글자는 Windows에 설치된 글꼴 하나로 그린다(`crates/ui-egui/src/system_fonts.rs`). 그런데 이 글꼴을 아랍어 글자(U+0627)가 있는지로만 고르기 때문에 Windows에서는 Segoe UI가 선택된다. Segoe UI에는 한글이 없다.
- 이 대체 글꼴의 경로를 바꾸는 설정이나 환경 변수가 없어서, 코드를 고치지 않고는 우회할 방법이 없었다.

## 2. PR 1: 한글 대체 글꼴 (#507)

- `system_fonts.rs`에 `hangul_fallback()`을 추가했다. `가`(U+AC00)가 있는 설치 글꼴을 하나 더 읽는다.
  - Windows: `malgun.ttf`(맑은 고딕), 없으면 `gulim.ttc`(굴림)
  - macOS: Apple SD Gothic Neo, AppleGothic
  - Linux: 나눔고딕, 은돋움, 백묵돋움
  - Noto Sans CJK는 프로젝트 규칙(`AGENTS.md` §1.1)이 Source Han 계열을 금지하므로 후보에서 뺐다.
- `theme.rs`의 `installed_font_definitions`에서 한글 글꼴을 모든 글꼴 묶음의 내장 글꼴 뒤, 기존 대체 글꼴(Segoe UI) 앞에 넣었다.
- 구조는 중국어 대체 글꼴을 추가하는 PR #426과 같은 형태(`load(paths, probe)` + 스크립트별 함수)로 맞췄다. 두 PR이 모두 받아들여져도 합치기 쉽다.
- `AGENTS.md` §1.4는 "설치된 글꼴은 하나만 읽는다"고 정하고 있다. 그래서 PR에 정책 변경 문구를 함께 넣고 관리자 결정을 요청했다. 근거로 형제 프로젝트 PhotoCraft가 같은 방식을 이미 병합한 사례(photocraft#185)를 들었다.
- PR 본문에 후속 제안도 적었다. 탭 제목과 북마크 제목은 전체를 지정한 로컬 글꼴로 그리자는 내용이다. 메뉴는 영어로 두더라도 파일 이름과 문서 내용은 다른 언어일 수 있기 때문이다.

## 3. PR 2: 두 페이지 끊어 보기 (#508)

- 새 보기 방식 **Two pages at a time**(`view.layout.two_page`, 설정 이름 `two-page`)을 추가했다. 기존 Two-page view는 두 쪽씩 나란히 놓고 연속 스크롤하는 방식이라서 그대로 두었다.
- 동작은 한 쪽 보기(Single page)와 같다.
  - 휠 한 칸, Page Down / Page Up, → / ← 키로 두 쪽씩 넘긴다.
  - 화면보다 크게 확대하면 휠은 쪽을 넘기지 않고 화면을 움직인다.
  - 쪽 맞춤(Ctrl+0)은 지금 보이는 두 쪽에 맞춘다.
  - 표지 쪽 옵션을 켜면 [1], [2, 3], [4, 5] 순서가 된다.
  - 마지막 쪽에서는 더 넘어가지 않는다.
- PDF가 `/PageLayout /TwoPageLeft` 또는 `/TwoPageRight`(두 쪽씩 표시)를 지정하면 이제 이 방식으로 연다. `/TwoColumn…`(두 열 연속 스크롤)은 기존 Two-page view로 연다.
- 새 메뉴 이름의 번역을 8개 언어(cs, es, fr, ja, ru, te, zh-hans, zh-hant)에 넣었다. 업스트림 테스트가 모든 명령의 번역을 검사하기 때문이다. 직접 쓴 번역이라 PR 본문에 원어민 검토가 필요하다고 적었다.
- PR 본문에 설계 제안도 적었다. Continuous scrolling을 다른 보기 방식과 함께 켤 수 있는 옵션으로 만들자는 내용이다. 이 옵션이 꺼져 있으면 한 쪽이든 두 쪽이든 항상 끊어서 넘기고, 켜져 있으면 스크롤한다. PDF의 `/PageLayout`도 같은 구조다.
- 이 기능을 요청한 이슈나 PR은 없다. 관련 항목은 #70/#77(두 쪽 단위 이동), #188/#265, #187(두 쪽 보기 끝에서 화면 깜박임), #289, PR #365(보기 방식 유지)이다.

## 4. 개인용 빌드에만 넣은 변경

`personal/malgun-first` 브랜치의 커밋 "Personal: tab and bookmark titles prefer the installed Hangul face, fully hinted"에 있다.

- 탭 제목(`chrome.rs`)과 북마크 제목(`panels.rs`)은 `hangul-first` 글꼴 묶음으로 그린다. 맑은 고딕이 맨 앞이라서, 그 안의 영문과 숫자도 맑은 고딕으로 나온다. 메뉴와 도구 이름은 Inter 그대로다.
- 맑은 고딕에는 가로 방향까지 hinting을 적용한다(`HintingTarget::Mono`). 세로 획이 조금 더 선명해지는 대신, 영문 글자 간격이 약간 불규칙해질 수 있다.

## 5. 글자가 번져 보이는 이유

- Word와 같은 맑은 고딕을 써도 PdfCraft의 글자가 더 흐리게 보인다. 글꼴이 아니라 렌더링 방식의 차이 때문이다.
- Windows 프로그램은 ClearType으로 그린다. 픽셀 하나를 빨강, 초록, 파랑 세 칸으로 나눠 가로를 세 배 정밀하게 그리는 방식이다. PdfCraft가 쓰는 egui는 회색 음영으로만 가장자리를 처리한다.
- 업스트림은 이미 정수 픽셀 정렬과 감마 보정(#76)을 적용해 두었다. 그 이상은 egui의 글자 렌더러를 고쳐야 해서 현실적이지 않다.
- 돋움이나 굴림으로 바꿔도 나아지지 않는다. 예전 프로그램에서 선명했던 이유는 글꼴 안의 작은 크기용 비트맵 덕분인데, egui는 그 비트맵을 쓰지 않는다.

## 7. 빌드와 실행 (PowerShell)

craft-fonts는 릴리스와 같은 버전(`abb8331`)으로 `z:\Github\pdfcraft\craft-fonts`에 받아 두었다.

```powershell
cd z:\Github\pdfcraft\pdfcraft
git checkout personal/malgun-first
$env:CRAFT_FONTS_DIR = "z:\Github\pdfcraft\craft-fonts"
cargo build --release -p pdfcraft
Copy-Item .\target\release\pdfcraft.exe "C:\program portable\pdfcraft.exe"
```

- 릴리스 빌드는 처음부터 하면 5분쯤 걸린다.
- 실행 중인 `pdfcraft.exe`는 덮어쓸 수 없으므로, 복사하기 전에 앱을 닫는다.
- 업스트림 품질 기준: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --no-fail-fast`, `cargo xtask wasm`, `cargo xtask assets`, `cargo xtask layers`, `cargo xtask parity`
- `cargo xtask wasm`을 돌리려면 wasm 타깃이 필요하다: `rustup target add wasm32-unknown-unknown`
- 번역 파일(`*.tsv`)을 고치면 `ATTRIBUTION.toml`의 SHA-256도 갱신해야 `cargo xtask assets`가 통과한다.

## 8. 알아 둘 점

- **빌드 폴더 용량:** `target`이 82 GB까지 커졌다. 대부분 테스트 실행 파일마다 생기는 디버그 정보(`.pdb`, 개당 약 570 MB)와 증분 빌드 캐시다. 코드를 고칠 때마다 새 파일이 쌓이므로, PR이 끝나면 `cargo clean`으로 지운다.
- **이 PC에서만 실패하는 테스트:** `i18n::tests::windows_display_language_query_returns_a_locale_tag`는 수정 전 main에서도 실패한다. Windows가 선호 언어를 여러 개 돌려주기 때문이고, PR #426이 이 테스트를 고친다.
- **시스템 글꼴과 스크린샷:** 프로젝트 규칙상 시스템 글꼴이 보이는 스크린샷은 공개하지 않는다. 그래서 PR에는 스크린샷을 첨부하지 않았다.
- **샘플 PDF:** 저장소에 커밋하는 문서도 asset으로 취급되어 `ATTRIBUTION.toml` 등록이 필요하다. 그래서 PR에는 PDF 파일을 넣지 않았고, 확인에는 합성 PDF(`한국어 테스트_문서.pdf`, 7쪽짜리 숫자 PDF)를 썼다.
- **설정 공유:** 개인용 빌드와 v0.4.0은 Windows 사용자 폴더의 같은 설정을 쓴다.
